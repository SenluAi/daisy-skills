# Skill：写给代理的文档

> 来源：改写自 mattpocock/skills 的 `writing-for-agents`（原文归档在 `productivity/writing-for-agents.md`）。
> 用途：写任何「给 AI 看」的文档——技能文件、`AGENTS.md`、索引、说明——都照这套来。

## 触发场景
- 用户说「把这个经验沉淀成技能」「更新一下索引」「写个说明给你自己看」。
- 我准备新建/修改 `Daisy-Skills` 里的任何文件时，自动启用。
- 不适用：写给**人**看的对外文章（那种要照顾阅读体验，不是触发精度）。

## 前置确认
- **自动获取（不要问用户）**：现有索引、同类技能文件、环境里能查到的路径与版本。
- **需要问用户的情况**：只在要新增**触发词**或改变自动化授权范围时确认一次。

## 执行步骤
1. **先写触发词**：开头一句话说明 + 列出「什么场景该打开我」，一个分支一个触发词，不堆同义词（同义词是同一个分支写了两遍）。完成判据：只看元数据就能判断该不该用这个技能。
2. **分两层摆放**：每个分支都要的（步骤主线）写在文件里；只有某些分支才用到的细节推到另一个文件，用触发词引过去（渐进披露）。完成判据：主线读起来只有必要步骤，没有岔路。
3. **就近归类**：一个概念的「是什么 + 规则 + 坑」放在同一标题下，别散在全文各处。完成判据：读一段就能带走它周边的信息。
4. **每步写完成判据**：写清「怎么算这一步做完了」，判据要能核对（「逐个核对文件名」强于「检查一下」）。完成判据：没有一步是「做到感觉可以为止」。
5. **用正面指令**：写「只提交这些文件」，而不是「不要提交别的文件」——禁止句会把被禁行为拉进视野。硬性红线才可以写禁止，并同时给出正确做法。
6. **找领先词**：能用模型自带的紧凑概念（如「红-绿循环」「一次性子弹」）压缩的，就压成一个词反复用；别自造没人认识的新词。完成判据：全文没有三处重复描述同一个概念。
7. **剪枝一遍**：逐句问「这句会不会改变默认行为？」——不会就整句删。别重复环境里能查到的东西（脚本、目录结构、`--help`），只留查不到的：没写下来的约定、当初为什么这么选、踩过的坑。完成判据：文件删到没有一句话是为了「填满篇幅」。
8. **登记索引**：新增/改名后，回 `README.md` 索引表补一行。完成判据：索引里的路径与文件名完全一致。

## 常见坑
- 只增不减：文件越积越厚，久了要靠「往下刨」才知道哪句还有效——每次编辑顺手删掉过时的。
- 同一规则在两个文件里各写一遍，改的时候必然漏一处（单一事实来源）。
- 把技能当论文写：读者是模型，短比全重要；细节多就拆文件，用触发词指过去。
- 触发词写得太泛（如「处理文档」）：匹配不准，等于白写。
- 一次写太长：超长文件会稀释注意力，主线步骤会被参考内容埋住。
